## Main product finding

The technical baseline is sound, but v0.1 still feels more like a study workbench than a high-repetition interview lab. The highest-value next change is the attempt shell, not a larger question bank.

Recommended desktop shell:

```text
┌────────────────────────────────────────────────────────────────────┐
│ topic / difficulty / timer / bookmark                prev · next   │
├─────────────────────────────┬──────────────────────────────────────┤
│ QUESTION                    │ EDITOR / CANVAS                      │
│ Task | Data | Schema | Hint │                                      │
│ constraints / fixtures      │                                      │
├─────────────────────────────┴──────────────────────────────────────┤
│ Results | Explanation | Visual | Notes | History        collapse  │
└────────────────────────────────────────────────────────────────────┘
```

The objective is one-screen practice with resizable panes. Results should open after Run/Check; Explanation should never reveal itself automatically. Visual should host exercise-specific explanations such as join flow, ERD, DAG, filter propagation, Spark stage metrics or architecture comparison.

## Workspace findings

### Code Lab

Keep real SQL execution and drafts. Add a stronger editor, visible schema/data fixtures, expected-vs-actual test diffs, dialect-aware SQL analysis, interview rubrics and visual explanations for joins, GROUP BY grain, windows and logical query processing.

### Model Lab

The current table/relationship/KPI combination is the correct direction. Extend it to arbitrary entities, columns, keys, relationship cardinality/filter direction, multiple measures and explicit filter-propagation traces. Use DBML/JSON and PBIP/TMDL-shaped text fixtures rather than trying to recreate Power BI Desktop.

### Pipeline Lab

The current editable DAG plus retries/failures is useful. Add typed nodes and semantics: Airflow trigger rules, branches, sensors, pools/concurrency, catchup/backfill; ADF Copy/Lookup/ForEach/Until/parameters/watermarks; dbt sources/models/tests/snapshots/incremental lineage. Code/config and graph should be two views of one underlying exercise state.

### Systems Lab

Use specialized renderers rather than review-only text:

- Terraform/OpenTofu: HCL editor, resource extraction, dependency graph and deterministic lint-style checks; never claim a real plan.
- Kubernetes/Docker: YAML/Dockerfile editor, schema/AST diagnostics, resource relationships and troubleshooting scenarios; no cluster required.
- Spark performance: Spark-UI-inspired synthetic investigations with stage DAG, partition sizes, task duration distribution, shuffle, spill, executor concurrency, join strategy and file metrics. Ask the learner to diagnose skew, shuffle, small files, partitioning, broadcast opportunities and UDF overhead.
- Cloud architecture: constraint-driven design with service roles, explicit requirements, cross-cloud equivalence and trade-off rubrics.

## Product organization

Keep four top-level labs for navigation simplicity:

1. Code Lab — SQL, Python, pandas, algorithms, Spark/PySpark syntax, Git/Linux.
2. Model Lab — dimensional modeling, Power BI/DAX/TMDL-shaped semantic models and KPIs.
3. Pipeline Lab — Airflow, ADF, dbt and generic orchestration/reliability.
4. Systems Lab — cloud architecture, Spark performance, Terraform/OpenTofu, Kubernetes/Docker and storage formats.

Internally, do not hard-code four page types. Each exercise should separately declare a renderer (`code-editor`, `terminal`, `semantic-model`, `dag-editor`, `architecture-editor`, `config-editor`, `performance-investigation`, `multi-choice-reasoning`) and an execution contract (`execute`, `analyze`, `simulate`, `review`).

## Release recommendation

Do not add hundreds of questions yet. First make two or three high-fidelity exercise types per workspace excellent; then scale the content pack. Preserve stable exercise IDs, import/migration behavior and explicit simulation boundaries.
